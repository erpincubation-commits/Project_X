# P2P business problem map

Reviewed 28 November 2026 against source baseline 0.2.0 / schema 16. This maps the requested problems to existing behaviour and proposed work. A proposed item is not implemented, deployed, approved financial policy, or a production-readiness claim. The [Phase One assessment](P2P_PHASE_ONE_ASSESSMENT.md) records dependencies and acceptance criteria. Core workflows use the local server and database; external transmission is separately selected and approved.

**Delivery objective:** complete Phase Two across all applicable problem groups before proceeding to Phase Three. Phase Two is not complete while required capabilities or their end-to-end verification remain outstanding. The approval and invoice visibility cues below are incremental changes, not completion of the phase.

Reference practices include [ERPNext Buying](https://docs.frappe.io/erpnext/buying), [Microsoft procurement and sourcing](https://learn.microsoft.com/en-us/dynamics365/supply-chain/procurement/procurement-sourcing-overview), and [invoice matching](https://learn.microsoft.com/en-us/dynamics365/finance/accounts-payable/accounts-payable-invoice-matching). These describe possible practices, not mandatory requirements for every company.

| Problem group | Relevance and existing controls | Remaining work / practical response |
| --- | --- | --- |
| A. Manual procurement | Relevant: structured requests, master selection, status and history reduce re-entry; PO copies the approved request. Purchasing can record non-binding quotation recommendations or issue an order linked to an eligible quote with matching approved prices. Bypass outside ERP cannot be technically ruled out. | Split sourcing, quoted-price reapproval and linked order allocations; business policy, training and audit for off-system purchases. No mandatory external service. |
| B. Approval delays | Relevant: assigned request queue, submission, independent decision, withdrawal and reassignment exist. An assigned approver can hand the decision to another independent approver with a reason and history. The request register can filter by waiting time. Payment approvers have a separate current-round **Awaiting my decision** queue. | Threshold routing, timed delegation, automatic escalation and notification are not implemented; define policies and approval authority first. Submission time is not an SLA or automatic reminder. |
| C. Supplier data | Relevant: unique normalized code, validated contacts, status and history exist. Desktop save warns of matching supplier names, emails or phone digits. The server repeats this check for saves and JSON import commits and requires an audited review reference to proceed with a match; application writes serialize the review. Permitted users can filter suppliers with blank contact fields. Reference-only qualification and expiry tracking has an independent administrator review and a permission-scoped work queue for pending, rejected, expired and not-recorded suppliers. Once a qualification record exists, new orders require approval and unexpired validity; legacy suppliers without a record remain eligible only when REQUIRE_SUPPLIER_QUALIFICATION is false (default). Operators can enable it to require approved qualification for all new orders. Bank information is not stored. | Fuzzy/legal-identity duplicate detection, external registration validation, document custody, adoption of the configurable mandatory-qualification policy, and verified bank changes remain. A privileged direct database write can still bypass the application check. External registry verification is optional and needs separate approval. |
| D. Purchase orders | Relevant: orders derive from approved requests, preserve snapshots and track received quantities; remaining quantities can be cancelled. Purchasing can manually record supplier acknowledgement and an optional expected date, with versioned history. The order register can filter unreceived orders with overdue promises or outstanding for at least 30 calendar days; Purchasing Overview shows both counts to permitted users on load/refresh. | Controlled description amendments are implemented with independent approval and history. Commercial line amendments, supplier transmission, automatic delivery-date alert or configurable aged-open-order dashboard. Issued does not necessarily mean unreceived. Design change authority and partial allocation before adding commercial amendments. |
| E. Receipts | Relevant: partial goods receipts and service acceptances record evidence and post to GRNI; accepted services do not create stock. The goods receipt register can search delivery references, filter damaged deliveries, and show/filter UTC calendar-day lag between posting date and entry. | Quarantine, supplier returns and actual physical-delivery-to-entry metrics remain missing. The posting date is user entered, so the lag cue is not proof of physical arrival. Define accounting and inventory treatment before implementing returns. |
| F. Invoices | Relevant: AP invoices entered manually or previewed from validated single-invoice JSON use PO/receipt/tax selections, duplicate supplier/reference controls and statuses. | No bulk/OCR invoice ingestion or non-PO service invoice; invoice format ingestion and tax policy require bounded validation, audit and finance review. No OCR or AI dependency implied. |
| G. Matching exceptions | Relevant: three-way matching detects missing/excess receipt, price, tax/date issues; independent price exception acceptance is supported. An administrator can configure a unit-price tolerance, initially zero, with versioned audit; posting rechecks current policy. Receipt, quantity, date and tax controls remain mandatory. Accountants can assign or reassign held exceptions to independent active reviewers with a reason; unassigned, assigned-to-me and 24-hour waiting queues are permission scoped. | No automatic escalation or notification exists. Finance should review any tolerance before production use. |
| H. AP and payment | Relevant: due dates, reservations, two independent approvals, duplicate execution-reference control, AP reports and bank reconciliation exist. The supplier invoice register can filter upcoming balances, and the permitted payment register supports search and status filtering. Supplier finance screens show permission-scoped overdue, due-today and next-seven-day invoice counts on load/refresh. Transfers occur outside ERP. | No scheduled payment deadline notifications, early-payment discounts, verified supplier bank master or bank transmission. These need policy, accounting and security design; external connectivity is optional. |
| I. Visibility | Relevant: request counts/assigned queue, document statuses, AP ageing and financial reconciliation exist and require refresh. Purchasing/admin/auditor users can load a paged approval workload by current assignee, with 24/72-hour ageing and past-30-day latest-cycle decision duration. Finance users can see period totals for posted supplier invoices and stock/service items, delivery outcomes, issued and unaccepted order value, historical approval/rejection cycle details and completed per-approver assignment intervals, plus damaged-receipt and invoice-exception events grouped by supplier. | Department/category analysis and an approved accounting commitment ledger (the current unaccepted estimate is not one), an agreed SLA policy and a policy-defined supplier scorecard require definitions and reconciliation. Invoice totals are not payments or a GL reconciliation; exception counts do not assign supplier fault. |
| J. Usability and integration | Relevant: desktop workspaces link requests, orders, receipts and invoices. An order can load and open its related receipts and permission-scoped supplier invoices. Actions still span screens and unsaved state is local. JSON master imports and five permission-checked P2P CSV report exports are available. | Expand cross-document navigation, safe draft/retry continuity and broader register exports. Any integration needs contract, authentication, audit, replay and a local-network/offline-operating decision. |

The register's **Submitted** value is rendered in the desktop's local time for submitted requests. Reassignment does not restart the submission time; withdrawal and resubmission create a new submission. **Pending with** is the currently assigned approver, not an escalation owner. Visibility follows existing request permissions. Refresh requests to obtain updated server records; no automated notifications or deadline calculations are added.

## Item-level relevance and response ledger

Verification update, 28 November 2026: the isolated multi-role desktop harness completed with exit code 0, including the order's inline service-acceptance evidence and uninvoiced-quantity check after invoice posting. See the [team test guide](P2P_TEAM_TEST_GUIDE.md#automated-desktop-evidence--28-november-2026) for scope and limits. The remaining feature gaps in this ledger are unchanged.

The decisions below apply the group-level controls above to every stated problem. **Implemented** means present in the current source baseline; it does not mean deployed or accepted by the business. **Partial** identifies a useful local control with a material boundary. **Policy/integration dependent** means a safe implementation requires an authority rule, accounting decision, external provider or operating environment that has not been selected.

| A1 | Repeated manual data entry | Relevant — partial. Master selection, request-to-order copying and linked receipt/invoice allocations avoid rekeying known identities and quantities; single-invoice JSON preview supports structured entry. OCR/PDF/bulk ingestion and external-system exchange remain unselected. |
| A2 | Paper/email purchase requests | Relevant — implemented. Structured drafts, submission, assignment, decision and history provide the in-product request path. Organisational policy must require its use. |
| A3 | Duplicate information across systems | Relevant — partial. Shared supplier/item masters and document links reduce duplication inside the ERP; external master ownership and synchronization need an approved integration contract. |
| A4 | Inconsistent procurement procedures | Relevant — implemented for the supported path. Server-enforced states and roles standardise request, quote, order, receipt, invoice and payment steps; configurable company policy remains outstanding. |
| A5 | Poor request-status visibility | Relevant — implemented. Status counts, search, ageing, pending owner, assigned queue and history are permission scoped and refresh based. |
| A6 | Employees bypassing procurement | Relevant — policy dependent. The ERP records authorised activity and audit history, but cannot prevent off-system buying; training, purchasing policy and spend review are required. |
| B1 | Long approval cycles | Relevant — partial. Oldest-first queues, elapsed-time filters and workload reporting expose delays; thresholds and automatic escalation require approved policy. |
| B2 | Incorrect approval routing | Relevant — partial. Submitters choose an independent active approver and can reassign; deterministic authority-matrix routing is not defined. |
| B3 | Approver unavailability | Relevant — implemented for manual recovery. Requesters and current approvers can make reasoned handoffs to another independent approver; timed delegation is policy dependent. |
| B4 | No escalation mechanisms | Relevant — partial. Ageing and workload queues support manual escalation; automatic escalation/notification awaits SLA and delegation rules. |
| B5 | No pending-approval visibility | Relevant — implemented. Requests and payment batches expose permission-scoped assigned queues; matching exceptions expose ownership and waiting queues. |
| B6 | Excessive manual follow-ups | Relevant — partial. Central queues and ageing reduce status chasing; outbound reminders require an approved delivery channel and escalation policy. |
| C1 | Duplicate suppliers | Relevant — implemented as a bounded control. Normalised name/email/phone checks require an audited review reference for application saves and imports; legal-identity/fuzzy validation remains external or policy dependent. |
| C2 | Incomplete supplier data | Relevant — implemented for current fields. Contact-completeness filters expose blank email/phone; richer mandatory onboarding fields need an approved data policy. |
| C3 | Invalid tax/registration details | Relevant — partial. Reference-only qualification and independent review are implemented; authoritative registry validation requires jurisdiction and provider selection. |
| C4 | Unverified bank information | Relevant — not stored by design. Verified bank-master custody and maker/checker changes require security, privacy and payment-provider decisions before implementation. |
| C5 | Expired supplier documents | Relevant — implemented for recorded qualification validity. Expired/rejected/pending queues and the qualification order gate exist. A server-date renewal queue finds approved qualifications expiring today through 30 days ahead. Physical document custody and automatic reminders remain outside this control. |
| C6 | Missing supplier lifecycle controls | Relevant — partial. Active state, version/history, qualification review and order eligibility exist; full onboarding, periodic review and offboarding policy remain. |
| D1 | Manual PO creation | Relevant — implemented. Orders derive from approved INR requests and can link an eligible quote, preserving snapshots and avoiding free-form re-entry. |
| D2 | Inaccurate PO details | Relevant — partial. Approved request/quote checks, server totals and immutable snapshots reduce error; supplier confirmation remains manually recorded. |
| D3 | Uncontrolled amendments | Relevant — partial. Issued-order description changes require a Purchasing proposal, independent business decision, matching version and retained history. Commercial quantity/price amendments and split allocations still require a schema-backed revision model. |
| D4 | Missing supplier acknowledgements | Relevant — implemented as manual evidence. Purchasing records acknowledgement reference and expected date with versioned history; no supplier portal/transmission exists. |
| D5 | Poor delivery visibility | Relevant — implemented. Awaiting-acceptance, overdue-promise and aged-open filters/counts use accepted quantities and server dates. |
| D6 | Open/outdated POs | Relevant — implemented. Users can filter orders outstanding at least 30 days and cancel remaining quantities; the threshold is currently fixed. |
| E1 | Missing goods receipts | Relevant — partial. Invoice matching requires eligible accepted quantities and open-order filters expose missing acceptance; the system cannot detect an unreported physical arrival. |
| E2 | Partial-delivery discrepancies | Relevant — implemented. Receipts record partial accepted and damaged quantities and prevent over-acceptance. |
| E3 | Damaged/rejected goods unrecorded | Relevant — partial. Damaged quantities and filtered review are recorded; quarantine, return and disposal accounting are not yet approved. |
| E4 | Missing service acceptance | Relevant — implemented. Separate service acceptance records evidence and partial quantities, post expense/GRNI and create no stock. |
| E5 | Delay between receipt and update | Relevant — partial. Goods receipts and service acceptances expose recorded timestamps, UTC-calendar entry-lag cues and server-side filters. Service filters cover the selected order. The entered posting date remains user supplied; verified physical-arrival/completion capture needs an operational process or integration. |
| F1 | Manual invoice entry | Relevant — implemented for bounded structured input. A versioned single-invoice JSON preview fills a new unsaved AP draft after validation and explicit replacement consent; ordinary save/match/post controls remain. OCR/PDF and bulk ingestion remain pending. |
| F2 | Duplicate invoices | Relevant — implemented. Supplier/reference uniqueness checks and idempotent operations prevent supported-path duplicates. |

| F4 | Missing PO references | Relevant — implemented for the supported AP path. Supplier invoices require an order and eligible receipt/service allocation; non-PO invoices are outside scope. |

| F7 | Poor invoice-status visibility | Relevant — implemented. Search, status/exception/due filters, balances, deadlines and history are permission scoped. |
| G1 | PO/invoice price differences | Relevant — implemented. Matching detects variance; configurable tolerance and independent exception review are rechecked at posting. |
| G2 | Quantity mismatches | Relevant — implemented. Allocation and posting prevent invoicing beyond accepted, unbilled quantity. |
| G3 | Missing goods receipts | Relevant — implemented as a blocking match condition. It cannot be waived as a price exception. |
| G4 | Incorrect tax treatment | Relevant — implemented as a blocking match condition using tax snapshots/current eligibility; statutory policy still needs Finance approval. |
| G5 | Unclear exception ownership | Relevant — implemented. Accountants assign/reassign an independent reviewer with a reason and retained history. |
| G6 | Slow exception resolution | Relevant — partial. Assigned-to-me and 24-hour queues expose delay; automatic escalation awaits SLA/notification policy. |
| H1 | Delayed invoice approvals | Relevant — partial. Exception queues and due-date views prioritise action; general invoice approval routing is not separately configured. |
