# Phase One: P2P application assessment

**Reviewed:** 27 November 2026  
**Baseline:** working-tree source, application 0.2.0 / schema 10  
**Status:** source and documentation assessment; deployment, business acceptance and production readiness remain unverified.

## Method and evidence limits

Reviewed the desktop renderer and Electron main/preload, procurement and trade controllers and services, contracts, PostgreSQL migrations, test inventory, user guide and operational documents. The previous multi-role Electron run reported a pass for authentication, purchasing, accounting, inventory, trade, operations and sampled automated accessibility. This assessment did not rerun that suite, inspect the customer's live database, conduct interviews, benchmark a production-like workload or independently verify every screen and failure case. A passing test proves only its fixture and assertions. Current working-tree changes are not evidence that an installed client or database was upgraded.

The user-defined classification **existing and functional** means working correctly and meeting requirements. Because business requirements and independent acceptance have not been established, no capability is certified in that category. **Implemented, acceptance unverified** is used as an evidence qualifier. **Existing but defective** is reserved for reproducible incorrect behaviour; no new reproducible product defect was established by this review. Gaps are prioritised P0 (financial/security/recovery prerequisite), P1 (core P2P), P2 (controlled operational improvement), or P3 (conditional integration or optimisation). Priorities are proposed, not a commitment to a particular policy or jurisdiction.

## Architecture and operations

Windows Electron 45 hosts a React 19/TypeScript renderer built with Vite. The sandboxed renderer accesses a context-isolated preload; the Electron main process mediates API communication and holds session tokens in memory. A TypeScript NestJS 11/Express API enforces permissions and owns business transactions. PostgreSQL stores shared data. Contracts and validation use a shared package and Zod; Node requires at least 22.12. The application is a **desktop client connected to an application server and central database**, not a self-contained offline database per client. Multiple users can connect to the same server. Shared records require connectivity; offline editing and later sync are not provided.

The documented single-machine development launcher binds the API to loopback. A multi-machine installation needs a customer-managed HTTPS reverse proxy, trusted certificate, firewall, database roles, service management and monitoring. PostgreSQL must remain private. TLS-proxy confirmation is not itself TLS. The Windows NSIS installer supplies the desktop only; the development build is unsigned. The visible Project X ERP name and existing SMB ERP installer/profile identity differ. No external cloud or AI service is required for core workflows; registry advisory checks need internet, while bank transfer happens outside the application. External integrations require a separately approved design.

The database pool is configured for 10 connections, five-second connection timeout and ten-second statement timeout. Those values and the bounded customer-focused load harness are not proof of enterprise capacity. Structured server/desktop logs, request references and error handling exist; startup diagnostics intentionally avoid credentials. Server database errors can be generic to operators. Deployment must supply log retention, monitoring, alerting and protected access. See [verification](VERIFICATION.md) for scope and unresolved manual accessibility/load work.

Authentication includes password, mandatory TOTP MFA, one-use recovery codes, expiry and revocation; identity recovery requires two administrators. Nine fixed roles enforce server-side permissions; the desktop hides unavailable actions but does not replace API checks. History/audit, expected versions, transaction locks and idempotency are implemented. A database owner can bypass ordinary history triggers; evidence is not tamper-proof against a privileged database administrator.

Encrypted logical backup and restore-to-new-database tooling exists, with reconciliation checks and session revocation. Scheduling, off-host copies, key escrow, restricted roles, service installation and tested RPO/RTO remain operational responsibilities. Upgrade scripts and migration checksums exist; rollback must use a rehearsed matching release and recovery process. Do not infer a live migration or backup from source.

## Data and integration map

`erp_suppliers` and `erp_items` feed `erp_purchase_requests` and request lines; the request snapshots supplier/item versions. `erp_supplier_quotes` and quote lines reference requests and request lines; withdrawal has a separate immutable record. `erp_purchase_orders.request_id` is unique: one order per request. Order lines feed goods receipt lines, which link stock movements and journals. AP invoice headers reference the supplier/order and invoice lines can reference order/receipt lines and tax snapshots; posted invoices link journals. Payment allocations connect supplier invoices to a payment; payment decisions record separate approvers and execution links a journal. Accounts, periods, stock balances/movements, GRNI, AP and bank reconciliations support the financial chain. Users, sessions, audit events, record history and retry records support access and traceability. Exact numeric columns and database constraints protect quantities, amounts and references; triggers guard several financial records. Migrations 1–10 are the source baseline, not a statement about a deployed database.

Authenticated `/api/v1/procurement` and `/api/v1/trade` endpoints expose the implemented operations. JSON master-import preview/commit supports customers, suppliers and items, not financial transactions. There is no supplied bank transmission, supplier portal or messaging service. A proposed integration must define source/target, trust boundary, network availability, credentials, audit, idempotent retry, reconciliation and local alternative before implementation.

## Verification and acceptance plan

Before implementation, confirm business workflows, company structure, financial/tax policy, volumes, operating environment and data retention with accountable owners. Review proposed acceptance criteria rather than treating the reference product as a specification. Then execute API unit/integration and concurrent mutation tests, migration from populated copies, Electron role flows, failure/retry, security and sampled plus manual accessibility, backup/restore and accounting reconciliations in isolated staging. Report build/schema, fixture, environment and failures. Validate deployment certificates, restricted DB roles, restore time and alerting separately. The source review cannot establish whether the current installation passes those checks or whether the product is production-ready.

No P2P software, schema, configuration, company data or installation was changed as part of this assessment.
